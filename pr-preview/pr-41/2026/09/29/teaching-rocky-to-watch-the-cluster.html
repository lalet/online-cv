Teaching Rocky to Watch the Cluster

September 29, 2026
#openclaw #kubernetes #cilium #rbac #selfhosted

TLDR: I gave Rocky, my self-hosted Telegram bot, read-only access to my Kubernetes cluster so it could tell me when something’s actually broken. Four separate bugs stood between “I wrote the config” and a single kubectl get pods returning anything: a missing binary, a config file that silently reset itself, a firewall rule checking the wrong port, and a permission that doesn’t cover what I thought it covered. None of them showed up by reading documentation.

Rocky already had access to my GitHub repo, opening pull requests when I asked. Giving it eyes on the cluster itself felt like the natural next step, so it could flag a crash-looping pod instead of me finding out because a service quietly died overnight.

I figured that was an afternoon of work. A read-only role, a tool plugin that speaks Kubernetes, done by dinner. It took four separate, unrelated bugs, each one hiding behind the last, before a single kubectl get pods call actually returned anything.

The plan

Rocky runs as one pod with tight permissions on purpose: no access to secrets, no write access anywhere, and a default-deny network policy with an explicit allow list for every outside service it’s allowed to reach. Bolting cluster monitoring onto that meant four new pieces:

  • A read-only Kubernetes role bound to its service account, secrets excluded entirely
  • An MCP tool plugin so it could actually query the cluster instead of guessing
  • A network policy rule letting it reach the API server at all
  • A written house rule telling it what it’s allowed to act on unsupervised, since giving an LLM both cluster visibility and the ability to merge its own pull requests needed some ground rules first

The role and the network policy felt like the easy half going in. The tool plugin is where the whole afternoon went.

Bug one: there’s no such binary

The MCP server I picked wraps kubectl directly instead of talking to the Kubernetes API in its own code. Its tools are literally named kubectl_get, kubectl_describe, and so on. The container image Rocky runs in doesn’t ship a kubectl binary at all.

Fix: an init container downloads a static kubectl binary onto a shared volume, and the main container’s PATH gets extended to include it. Almost embarrassingly simple, except the shared directory couldn’t just be /usr/local/bin. That’s where the base image already keeps node, npm, and Rocky’s own binary, and mounting a volume there replaces the whole directory instead of adding to it. I found that out by breaking the container completely on the first try.

Bug two: the setting that wouldn’t stick

Getting that new PATH into the tool plugin’s own environment needed its own fix. Rocky’s config lives in a JSON file on disk, and any setting I wrote into that file during pod startup kept vanishing by the time the pod was actually ready. Something in the app’s own boot sequence rewrites the file after the fact, wiping out anything written before it finishes.

I caught this by checking the file’s last-modified timestamp against the container’s own startup log: whatever I’d written during startup was already gone before the app finished booting. The fix had to run after the app was fully up, not before.

Bug three: right door, wrong number

With the binary and its environment sorted, kubectl stopped erroring and started hanging instead. No response, no error, just silence until it gave up on its own.

A silent hang like that usually means a firewall, not the app. Watching my network policy engine directly confirmed it: the connection was being dropped, and dropped packets don’t send anything back, they just disappear. I’d written the rule against the API server’s internal service port. But the network layer swaps that address for the real backend server before deciding whether to let the connection through, and the real server listens on a different port than the service does. One number, wrong the entire time, and nothing about the symptom looked like a port problem.

Bug four: a permission is not a permission

Everything connected after that. kubectl get pods worked. kubectl logs did not: flat permission denied, even though the exact rule that let Rocky read pods should have covered logs too.

Turns out reading a pod’s logs is its own distinct permission in Kubernetes, separate from reading the pod object itself. Easy to miss if you’re thinking “can it see pods,” not “can it do this one specific thing.”

What actually made this fast

Two habits saved most of the afternoon.

Whenever a fix looked plausible but the real behavior stayed broken, I stopped trusting the config file and ran the actual thing: the tool call Rocky would really make, not just checking that a setting now had the right value on disk. Config being correct and behavior being correct are two different claims. I declared victory on the wrong one more than once.

The other habit I’d already learned the hard way, from the last time this blog covered Rocky falling over: my cluster’s GitOps setup reverts any change made directly against the live cluster if it isn’t also committed to the config repo, usually within a minute or two. I’d fix something, watch it work, then come back five minutes later convinced my own fix had broken again, when really it had just been quietly rolled back because I hadn’t committed it yet. What worked instead: confirm the fix with a fast manual test, then commit it right away, rather than iterating live for more than a few seconds at a stretch.

Where it landed

Rocky can now list pods, read logs, check deployment health, and keep an eye on the rest of the cluster on a standing half-hour timer, all read only, none of it able to touch anything even by accident. It only messages me when something’s actually wrong.

None of the four bugs showed up by reading documentation. Every one of them only showed up by testing the real behavior and watching what actually happened on the wire.
